## 1. Executive Summary

Kickru의 「벤치에서 발롱까지」는 축구 경기를 직접 조작하는 게임이 아니라, **한 명의 선수가 고교·유스 단계에서 시작해 프로 데뷔, 이적, 국가대표, 수상, 노화와 은퇴까지 살아가는 커리어를 압축해서 체험하는 라이프 시뮬레이션**이다.

핵심 강점은 그래픽이나 실시간 경기 조작보다 다음 다섯 요소에 있다.

1. **짧은 입력으로 긴 커리어를 생성하는 압축성**
2. **선택 → 시즌 결과 → 성장 → 다음 선택**이 반복되는 명확한 루프
3. 실제 축구 제도와 리그 구조를 활용한 높은 세계관 설득력
4. 커리어 말미에 과거 선택을 다시 의미화하는 **회고형 내러티브**
5. 로컬 저장 중심 구조와 서버 랭킹을 결합한 비교적 가벼운 운영 모델

즉, 장르적으로는 Football Manager의 축소판이라기보다 **BitLife + 축구 커리어 RPG + 스포츠 시뮬레이션**에 가깝다.

이 게임에서 벤치마킹 가치가 가장 높은 부분은 경기 엔진 그 자체보다 **“장기간의 인생을 몇 분 단위 의사결정으로 체험하게 하는 설계”**다.

# 3. 제품 포지셔닝

## 3.1 사용자가 구매하는 판타지

사용자가 실제로 원하는 것은 “축구 경기를 잘하는 경험”이 아니다.

> **내가 만든 선수가 어디까지 올라갈 수 있는가?**

라는 성장 판타지다.

게임은 첫 화면부터 이를 명확하게 보여준다.

```
벤치
  ↓
데뷔
  ↓
첫 골
  ↓
우승
  ↓
발롱도르
```

이 다섯 단계는 기능 설명이 아니라 게임 전체의 **Progress Fantasy**를 시각적으로 요약한다.

이는 좋은 온보딩 방식이다.

사용자는 상세 규칙을 몰라도 목표를 이해한다.

---

# 4. Core Loop

Kickru의 핵심 게임 루프를 단순화하면 다음과 같다.

```
선수 생성
   ↓
시즌 진행
   ↓
출전 / 성적 / 성장 계산
   ↓
커리어 이벤트 발생
   ↓
선택
 ├─ 훈련
 ├─ 계약
 ├─ 이적
 ├─ 임대
 ├─ 대표팀
 ├─ 기자회견
 ├─ 진로
 └─ 기타 전환점
   ↓
능력치 / 명성 / 역할 / 소속 변화
   ↓
다음 시즌
   ↓
...
   ↓
노화
   ↓
은퇴
   ↓
커리어 회고 + 랭킹
```

이 구조의 중요한 점은 **시즌 진행 자체가 보상 루프의 버튼**이라는 것이다.

실시간 조작 대신 버튼 한 번이 상당한 시간을 압축한다.

따라서 한 번의 플레이 세션 안에 사용자는 실제 스포츠 게임보다 훨씬 많은 “커리어 사건”을 경험한다.

---

# 5. 게임을 재미있게 만드는 4개 루프

## 5.1 Growth Loop

```
출전
→ 활약
→ 성장
→ 더 좋은 역할
→ 더 좋은 팀/대회
→ 더 큰 활약 기회
```

특히 “잠재력 = 자동 성장”이 아니라는 점이 중요하다.

잠재력이 높더라도 벤치에 있으면 성장하지 못한다.

따라서 사용자는 단순히 가장 유명한 구단을 고르는 것이 아니라

> 빅클럽 벤치 vs 약팀 주전

이라는 의미 있는 선택을 하게 된다.

이것이 **Opportunity Cost**를 만든다.

---

## 5.2 Career Choice Loop

게임은 일정 간격으로 커리어 전환점을 제시한다.

예:

- 육성 방향
- 이적
- 재계약
- 임대
- 주장
- 포지션 전환
- 기자회견
- 대표팀
- 은퇴 권고
- 병역 관련 선택

선택은 즉시 숫자를 올리는 단순 업그레이드가 아니라 **향후 커리어 상태를 바꾸는 분기**다.

좋은 선택형 게임에서 중요한 것은 “정답 찾기”보다 “내 선택이었다는 느낌”인데, Kickru는 이를 상당히 잘 활용한다.

---

## 5.3 Narrative Loop

```
선택
→ 사건
→ 기록
→ 후속 사건
→ 커리어 역사
→ 은퇴 후 회고
```

라이벌 팀 이적, 친정 복귀, 결승 설욕, 큰 부상과 복귀, 발롱도르 같은 사건은 단순 플래그로 끝나지 않는다.

은퇴 시 다시 **인생 이야기**로 호출된다.

이 때문에 과거의 데이터가 서사로 재사용된다.

기술적으로 매우 효율적인 내러티브 설계다.

새로운 스토리 콘텐츠를 무한히 작성하지 않아도

```
Event + Context + History
```

조합만으로 플레이어마다 다른 이야기를 만들 수 있다.

---

## 5.4 Prestige Loop

커리어 종료 뒤 랭킹이 존재한다.

```
개인 커리어
→ 은퇴
→ 서버 제출
→ 일일 랭킹
→ 다른 사용자와 비교
→ 새 커리어
```

싱글플레이 게임에 최소한의 소셜 경쟁을 추가한다.

서버는 모든 플레이를 실시간 관리할 필요가 없다.

**최종 결과만 서버에 올리는 구조**이기 때문에 비용 대비 효과가 크다.

---

# 6. Progression Design

## 6.1 육성 변수

공개된 정보로 보면 성장 시스템은 최소 다음 변수의 함수다.

```
Growth =
  Age
× PlayingTime
× Performance
× Health
× HiddenGrowthTrait
× Training/Events
```

실제 내부 공식은 공개되어 있지 않으므로 위 표현은 개념 모델이다.

핵심은 플레이어가 모든 변수를 직접 볼 수 없다는 점이다.

특히 숨겨진 성장 특성은 **불확실성**을 만든다.

“이번 선수는 어디까지 클까?”가 반복 플레이의 중요한 동기가 된다.

---

## 6.2 Potential의 역할

Potential은 단순 최대 레벨이 아니다.

```
Potential = Ceiling
Actual Growth = Opportunity × Performance
```

이 구조가 좋은 이유는 두 가지다.

1. 좋은 재능을 뽑았다고 게임이 끝나지 않음
2. 커리어 선택이 성장에 실제 영향을 미침

---

# 7. Position System

10개 포지션이 존재한다.

| 계열 | 포지션 |
|---|---|
| 공격 | ST, LW, RW |
| 미드필드 | CAM, CM, CDM |
| 수비 | CB, LB, RB |
| 골키퍼 | GK |

OVR이 포지션별 가중평균이라는 것은 중요한 설계다.

예를 들어 동일 능력치라도

```
ST → Shooting 가중치 ↑
CAM → Passing/Dribbling 가중치 ↑
CB → Defense/Physical 가중치 ↑
```

처럼 해석할 수 있다.

따라서 **능력치 배열이 곧 플레이 스타일**이 된다.

---

# 8. Aging & Career Arc

일반적인 육성 게임은 계속 강해지는 구조를 사용한다.

Kickru는 반대로

```
Growth
→ Peak
→ Decline
→ Retirement
```

를 반드시 경험하게 한다.

포지션에 따라 전성기 길이도 달라진다.

이 구조의 장점은 **한 커리어에 끝이 생긴다는 것**이다.

끝이 있어야 다음 캐릭터를 시작할 이유도 생긴다.

즉, 은퇴는 콘텐츠 종료가 아니라 **메타 리텐션 장치**다.

---

# 9. Event Architecture

이 게임의 확장성이 높은 이유는 “전환점 이벤트” 구조에 있다.

개념적으로 다음 데이터 모델을 예상할 수 있다.

```ts
Event {
  id
  triggerCondition
  title
  description
  choices[]
}

Choice {
  label
  successProbability?
  requirements?
  effects
  followupFlags
}
```

예를 들어 기자회견은

```
Season Context
→ Question
→ 4 Responses
→ Probability
→ Result
→ Stat/Reputation change
→ News/Fan reaction
```

처럼 처리할 수 있다.

패치노트에서 기자회견 답변마다 성공 확률과 성공/실패 결과가 보인다는 점이 확인된다.

이 구조는 교육용 게임이나 인생 시뮬레이션에서도 재사용 가치가 매우 높다.

---

# 10. Economy

상점은 커리어에서 번 돈을 사용하는 **Money Sink** 역할을 한다.

확인 가능한 특징:

- 시즌마다 새 상품 3개
- 한 시즌에 하나만 구매
- 저가 아이템부터 슈퍼카·요트·전용기·개인 경기장까지 단계적으로 확장
- 능력치/성장/부상 저항 등 게임 효과 제공

중요한 점은 단순 숫자 소비가 아니라

```
Income
→ Lifestyle Item
→ Career Effect
```

로 연결한다는 것이다.

돈이 “쌓이는 숫자”가 아니라 선택 자원이 된다.

---

# 11. Transfer & Contract System

Kickru의 이적 시스템은 커리어 판타지를 만드는 핵심 장치다.

구단의 관심은 단순 OVR만 보는 것이 아니라

- 소속팀 수준
- 선수 능력
- 최근 활약
- 선수 역할
- 연령
- 구단 수준

등을 함께 반영하도록 지속적으로 조정되고 있다.

특히 패치노트에

> 약팀을 이끌며 압도적으로 활약하면 더 높은 수준의 구단에서도 제안

이라는 로직이 명시되어 있다.

이 구조는 **성과가 이동성으로 변환되는 시스템**이다.

```
Performance
→ Reputation
→ Better Offers
→ Higher Competition
→ Higher Prestige
```

---

# 12. Real-world Football as Content Database

Kickru가 작은 웹게임임에도 깊어 보이는 가장 큰 이유 중 하나다.

게임은 현실 축구의 복잡성을 콘텐츠로 활용한다.

예:

- K리그 승강
- K3/K4
- 유럽 승격 플레이오프
- 스플릿 리그
- 클럽 월드컵
- UEFA 챔피언스리그
- 대표팀 대회
- 병역
- 상무
- 준프로
- 대학 진학
- 춘추제 / 추춘제

즉,

```
Real Football Rule
→ Simulation Rule
→ Player Choice
```

로 변환한다.

따라서 자체 세계관을 처음부터 쓰는 비용이 줄고, 축구팬이 이미 가진 배경지식이 게임의 깊이로 전환된다.

# 13. Match Simulation

실제 공개 정보상 경기 전체를 사용자가 직접 컨트롤하는 구조는 아니다.

대부분 시즌 단위 시뮬레이션이며 중요한 경기/결승/승강 플레이오프 등에서 “중계” 경험을 제공하는 방향으로 보인다.

이 접근은 매우 효율적이다.

모든 경기를 자세하게 보여주면 반복성이 커진다.

대신

```
일반 경기 → 압축
중요 경기 → 확대
```

하는 **Narrative Zoom** 방식을 사용한다.

사용자에게 의미 있는 순간만 상세하게 보여주는 것이다.

# 14. UI / UX 분석

## 14.1 Landing Page

첫 화면은 기능 메뉴보다 “인생 경로”를 먼저 보여준다.

- 벤치
- 데뷔
- 첫 골
- 우승
- 발롱도르

이는 게임의 목표를 매우 빠르게 이해시키는 장치다.

### 좋은 점

- 복잡한 룰 설명보다 감정적 목표를 먼저 전달
- 축구팬이 즉시 의미를 이해
- 모바일에서도 읽기 쉬운 세로 흐름

---

## 14.2 Progressive Disclosure

처음부터 모든 시스템을 노출하지 않는다.

커리어가 진행되며

- 계약
- 이적
- 대표팀
- 상점
- 노화
- 은퇴

같은 시스템이 자연스럽게 의미를 갖는다.

이는 UI 복잡도를 낮춘다.

---

## 14.3 Choice Card UX

이 게임의 핵심 UI는 결국 **선택 카드**다.

좋은 선택 UI는 다음 정보를 가진다.

```
상황
→ 선택지
→ 예상 효과/위험
→ 결정
→ 결과
```

2026-11-02 기자회견 업데이트에서 성공 확률과 성공·실패 결과를 선택 전에 보여 주도록 바뀐 것은 중요한 UX 개선이다.

“무슨 일이 일어날지 전혀 모르는 랜덤”보다 **Risk-informed Choice**를 제공한다.

# 15. Information Architecture

사이트는 단순 게임 화면만 존재하지 않는다.

확인 가능한 정보 구조:

```
/
├─ 게임
├─ rankings
├─ about
├─ guide
├─ guides
├─ patch-notes
├─ privacy
├─ terms
├─ contact
└─ site-map
```

특히 `guide`와 `guides`가 분리되어 있다.

- Guide = 조작/저장/랭킹 같은 공식 사용법
- Guides = 성장/이적/수상 등 전략 콘텐츠

이는 SEO와 사용자 학습 양쪽에 유리하다.

게임 내부 튜토리얼을 과도하게 만들지 않아도 외부 문서가 보완한다.

---

# 16. Save Architecture

## [확인]

게임 진행은 현재 브라우저에 자동 저장된다.

브라우저 데이터 삭제나 기기 이동 시 데이터가 사라질 수 있기 때문에 파일 Export/Import 기능을 제공한다.

서버에는 전체 커리어가 자동 백업되지 않는다.

## [추정]

이 구조는 브라우저의 다음 중 하나를 사용할 가능성이 높다.

- localStorage
- IndexedDB

커리어 데이터 크기와 구조를 생각하면 IndexedDB가 더 확장성 있는 선택이지만 실제 구현은 내부 코드를 확인하지 않아 단정할 수 없다.

### 구조적 장점

- 회원가입 불필요
- 서버 DB 비용 최소화
- 개인정보 보관 최소화
- 오프라인/저지연 플레이에 유리

### 단점

- 기기 간 동기화 어려움
- 저장 삭제 위험
- 랭킹 부정행위 검증 어려움

---

# 17. Server Architecture

공개 가이드와 랭킹 정책을 기준으로 가장 합리적인 구조는 다음과 같다.

```
[Browser]
  │
  ├─ Career Simulation
  ├─ Game State
  └─ Local Save
        │
        │ retirement
        ▼
[Ranking API]
        │
        ▼
[Ranking DB]
```

즉 **게임 본체는 client-heavy**, 경쟁 기능만 server-backed인 구조다.

이 모델은 소규모 개발자가 운영하기 매우 적합하다.

---

# 18. Ranking Design

랭킹 비교 순서:

1. 발롱도르 횟수
2. 최고 OVR
3. 개인상 횟수
4. 공격포인트

이 순서는 매우 의도적이다.

단순 득점 랭킹이었다면 공격수 편향이 심해진다.

발롱도르와 OVR을 앞에 두면서 커리어 전체 성취를 반영한다.

다만 골키퍼·수비수와 공격수의 공정한 비교는 여전히 어려운 구조일 수 있다.

따라서 베스트11을 포지션별로 별도 구성하는 것이 보완책 역할을 한다.

---

# 19. Anti-cheat의 구조적 한계

로컬 게임 상태를 클라이언트가 보유하기 때문에 완전한 서버 검증은 어렵다.

운영 측도 가이드에서 랭킹이 “조작을 완전히 검증하는 공식 대회용 랭킹은 아니다”라고 명시한다.

패치노트에서는 상위권 기록 서버 검증, 매크로/도배 기록 삭제 정책이 추가되었다.

이 선택은 현실적이다.

```
완전한 보안
vs
운영 비용
```

사이에서 후자를 낮춘 것이다.

소규모 비동기 싱글플레이 게임이라면 합리적인 trade-off다.

# 22. Narrative Engine 추정

은퇴 시 커리어 이야기를 생성하려면 게임 중 의미 있는 사건을 기록해야 한다.

예상 구조:

```ts
CareerMoment {
  season
  age
  type
  club
  opponent?
  competition?
  result?
  relatedClub?
  choice?
```

그리고 은퇴 시

```
Moments
→ importance sorting
→ narrative templates
→ chronological story
```

방식으로 조립할 수 있다.

LLM 없이도 상당히 풍부한 개인화 스토리를 생성할 수 있다.

이 설계는 **학생 성장 기록, 역사 체험, 인생 게임, 경제 게임**에도 그대로 응용 가능하다.

# 23. Why It Is Addictive

Kickru는 강한 액션 피드백 대신 **“다음 시즌에는 무슨 일이 생길까?”**를 이용한다.

핵심 심리 루프:

```
Uncertainty
+ Growth
+ Ownership
+ Rare Events
+ Long-term Goal
```

### Uncertainty
숨은 성장 특성, 랜덤 사건, 부상, 제안.

### Growth
OVR과 커리어 위상이 상승.

### Ownership
사용자가 만든 선수.

### Rare Events
발롱도르, 대형 이적, 국가대표 우승, 레전드.

### Long-term Goal
은퇴까지 하나의 완결된 인생.

이 다섯 요소가 결합되어 “한 시즌만 더” 행동을 만든다.

---

# 24. 가장 좋은 설계 포인트

## A. 한 버튼이 시간을 크게 움직인다

일반적인 게임은 10분 플레이해도 세계 시간이 10분 흐른다.

이 게임은 클릭 몇 번으로 1년이 흐를 수 있다.

따라서 **결과 밀도**가 높다.

---

## B. 숫자를 서사로 바꾼다

```
OVR 85
```

만 보여주는 것보다

```
약팀 주전
→ 깜짝 우승
→ 빅클럽 제안
→ 친정팀 상대 결승
→ 발롱도르
```

처럼 숫자가 사건으로 변환된다.

---

## C. 현실 규칙을 시스템 콘텐츠로 사용

새로운 판타지 세계를 만들지 않고 실제 축구 생태계를 활용한다.

---

## D. 끝이 있는 육성

은퇴 때문에 플레이가 완결된다.

완결 후 새 선수를 시작할 이유가 생긴다.

---

## E. 서버를 꼭 필요한 곳에만 사용

커리어는 로컬, 랭킹은 서버.

비용 대비 매우 좋은 구조다.

---

# 25. 개선 가능성이 있는 지점

## 25.1 시즌 진행의 반복성

커리어가 길어질수록

```
진행 → 결과 → 진행 → 결과
```

패턴이 반복될 수 있다.

이를 줄이려면

- 시즌마다 다른 목표
- 라이벌 시스템
- 감독/구단 관계
- 장기 퀘스트
- 개인 목표

같은 중기 목적이 필요하다.

---

## 25.2 Hidden Potential과 리세마라

숨은 재능은 반복 플레이를 만들지만 지나치면

> 좋은 잠재력 나올 때까지 새 게임

행동을 유발할 수 있다.

실제로 패치에서 고교 성장 속도가 재능을 직접 드러내지 않도록 바꾼 점은 이 문제를 완화하는 설계로 볼 수 있다.

---

## 25.3 랭킹 공정성

클라이언트 저장 구조에서는 완벽한 검증이 어렵다.

진짜 경쟁게임으로 확대하려면

```
seed
+ signed progression events
+ server validation
```

같은 구조가 필요하다.

현재 게임에는 오히려 과도할 수 있다.

---

## 25.4 신규 사용자 정보량

축구 규칙이 깊어질수록 신규 사용자가 이해해야 하는 개념이 늘어난다.

따라서

- Beginner Mode
- Advanced Mode
- Contextual Tooltip

같은 계층적 설명이 효과적일 수 있다.

---

# 26. 재사용 가능한 Game Design Patterns

## Pattern 1 — Accelerated Life Simulation

```
1 Click
→ 1 Month / 1 Season / 1 Year
```

활용:
- 운동선수
- 연예인
- 기업가
- 음악가
- 학생
- 정치인
- 역사 인물

---

## Pattern 2 — Opportunity vs Prestige

```
Strong Organization + Low Opportunity
vs
Weak Organization + High Opportunity
```

매우 강력한 선택 구조다.

---

## Pattern 3 — Hidden Trait

플레이어가 모든 능력을 처음부터 알지 못하게 한다.

반복 플레이를 만든다.

---

## Pattern 4 — Career Memory

중요 사건을 기록했다가 후반에 다시 활용한다.

```
Past Decision
→ Future Consequence
```

---

## Pattern 5 — Local-first + Shared Result

```
Full Simulation = Local
Final Score = Server
```

소규모 웹게임에 매우 유용하다.

---

# 27. 다른 게임 개발 시 가져올 요소 / 가져오지 말아야 할 요소

## 적극 벤치마킹

- 시즌 단위 시간 압축
- 사건 기반 커리어
- Opportunity vs Prestige 선택
- 숨은 성장 특성
- 노화와 은퇴
- 커리어 회고
- 로컬 우선 저장
- 종료 결과만 랭킹 서버에 전송
- 실제 세계 규칙을 시뮬레이션 규칙으로 재구성

## 그대로 복제하면 안 되는 요소

- 구체적 UI 디자인
- 고유 문구
- 브랜드
- 이미지/아트
- 독자적인 이벤트 텍스트
- 데이터 표현을 포함한 원본 저작 표현

벤치마킹 대상은 **패턴과 시스템**, 아닌 것은 **표현물**이다.

# 28. 교육용·놀 서비스 관점에서 특히 참고할 부분

Kickru 구조는 교육 게임에도 매우 적합하다.

예를 들어 학생 경제 시뮬레이션이라면:

```
학생 캐릭터 생성
→ 경제 활동
→ 선택
→ 수입/지출
→ 투자/위기
→ 커리어 변화
→ 장기 결과
→ 회고
```

역사 체험이라면:

```
인물 생성
→ 시대 사건
→ 선택
→ 신분/재산/관계 변화
→ 다음 시대
→ 생애 회고
```

핵심은 **문제 정답형 게임이 아니라 시스템 안에서 선택 결과를 경험하게 하는 것**이다.

# 30. Craft Anything 관점의 최종 분해

Craft Anything이 강조하는 **Study → Build → Check**로 요약하면 다음과 같다.

## Study

우리가 관찰해야 할 것은 페이지 모양이 아니라:

- 어떤 상태가 존재하는가
- 어떤 이벤트가 상태를 바꾸는가
- 어떤 데이터가 지속되는가
- 어떤 결과가 사용자에게 보상으로 느껴지는가

이다.

## Build

유사한 재미를 만들고 싶다면 먼저 구현해야 할 순서는:

1. Player State
2. Season Simulation
3. Growth
4. Events
5. Career History
6. Retirement
7. Ranking

이다.

그래픽은 이 이후다.

## Check

구현 후 다음 질문으로 검증할 수 있다.

- 5분 안에 첫 의미 있는 선택이 발생하는가?
- 10분 안에 성장 체감이 있는가?
- 서로 다른 두 커리어가 실제로 다른 이야기를 만드는가?
- 강팀/약팀 선택에 trade-off가 있는가?
- 은퇴했을 때 자신의 커리어를 다시 보고 싶은가?
- 바로 새 선수를 만들고 싶은가?

여기에 “예”가 많을수록 Kickru가 가진 핵심 재미 구조를 잘 이해한 것이다.

# 31. 결론

Kickru의 가장 중요한 혁신은 복잡한 축구 데이터를 많이 넣은 것이 아니다.

핵심은

> **커리어 전체를 짧은 선택들의 연속으로 압축하고, 그 선택의 누적을 마지막에 하나의 인생 이야기로 돌려주는 구조**

다.

따라서 이 서비스를 참고해 새로운 게임을 만든다면 가장 먼저 베껴야 할 것은 화면이 아니라 다음 구조다.

```
Create
→ Simulate
→ Choose
→ Grow
→ Remember
→ Decline
→ Retire
→ Reflect
→ Replay
```

이 루프가 Kickru의 제품 핵심이다.
